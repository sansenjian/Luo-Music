# Android 端可行性说明

本文用于评估 LUO Music 从现有 Web / Electron 架构扩展到 Android 应用的实现难度、风险和推荐路线。

## 结论

实现 Android 端可行，但建议第一个版本只完成移动端 UI 和在线搜索，不追求播放器完整闭环，更不追求与 Electron 桌面端完全等价。

- 做移动端 UI、平台切换、关键词搜索、搜索结果列表和基础状态反馈：难度中低到中等。
- 播放、登录、歌单、收藏、缓存、后台播放等能力应放到后续版本。
- 完整迁移桌面端能力，例如本地音乐库扫描、桌面歌词、插件运行时、Windows 媒体控制、托盘和窗口能力：难度偏高。
- 当前项目已有 `src/platform/` 平台收口层，对新增 Android 适配是利好。

## V1 范围

第一个 Android 版本的目标是验证“这个项目能以 Android 应用形态打开，并提供可用的移动端搜索体验”。

应包含：

- Android 应用可以安装、启动和进入主界面。
- 首页、搜索栏、平台选择和搜索结果列表适配手机屏幕。
- 支持在线搜索关键词并展示结果。
- 搜索过程具备 loading、empty、error 等基础状态。
- Electron-only 功能入口在 Android 端隐藏或禁用。

不包含：

- 歌曲播放。
- 后台播放和通知栏媒体控制。
- 登录、用户歌单、收藏同步。
- 本地音乐库扫描。
- 歌词、桌面歌词和锁屏展示。
- 下载、离线缓存和外部插件。

## 推荐技术路线

优先选择 Capacitor，将现有 Vue / Vite Web 应用打包进 Android WebView，并通过原生插件补齐移动端能力。

基础流程：

1. 先确保 Web 构建产物可作为独立静态资源运行。
2. 引入 Capacitor 配置，设置 Android 包名和 Web 构建目录。
3. 添加 Android 工程并通过 Android Studio 调试。
4. 在 `src/platform/` 增加 Android / Capacitor 平台服务实现。
5. V1 只保留最小 Android 容器能力，暂不接文件系统、媒体通知、后台播放等原生插件。

Capacitor 官方要求现有 Web 应用至少具备 `package.json`、独立的 Web 构建目录以及构建目录根部的 `index.html`。

## 当前项目的有利条件

- Vue 3 + Vite 本身适合被 Capacitor 包装为移动应用。
- `src/platform/` 已经隔离 Web 与 Electron 差异，新增 Android 平台服务不必大面积改 UI。
- 播放器核心主要运行在渲染侧，在线播放路径有机会复用。
- 现有 `isMobile()` 判断已经能服务一部分移动布局分支。
- 文档和模块边界已经明确，适合继续按平台能力拆分。

## 主要难点

### Electron 专属能力不能直接复用

以下能力需要降级、重写或暂缓，但它们不阻塞 V1：

- `electron/` 主进程、preload、IPC。
- `better-sqlite3` 和本地音乐库相关 Node 能力。
- 桌面歌词浮窗。
- Windows SMTC、托盘、窗口控制。
- 外部插件 Node 运行时。
- 依赖本地进程或 `localhost` 服务的 API 聚合逻辑。

### Android 音乐应用后续需要原生能力

如果后续要做完整播放器体验，Android 端通常需要额外处理：

- 后台播放。
- 锁屏和通知栏媒体控制。
- 耳机、蓝牙和系统媒体按键。
- 音频焦点。
- 存储权限和媒体库读取。
- WebView 中的 Cookie、跨域、下载和缓存策略。

### UI 需要移动端重排

V1 的重点是移动端 UI 验证。桌面播放器 UI 不能只缩放到手机屏幕，需要重新确认：

- 首页、搜索、平台选择和搜索结果列表的主流程。
- 底部播放器和全屏播放页在 V1 可先隐藏或占位。
- 设置页分组和触摸操作区域。
- 长列表性能和虚拟滚动表现。

## 推荐分阶段计划

### 阶段 1：V1 UI 与在线搜索

目标是尽快跑通一个可安装 APK，并验证移动端搜索体验。

- 引入 Capacitor Android 工程。
- 复用 Web 构建产物。
- 增加 Android 平台识别。
- 禁用 Electron-only 功能入口。
- 调整首页、搜索栏、平台选择和搜索结果列表的移动端布局。
- 验证在线搜索、加载态、空状态和错误状态。

成功标准：

- 可以在 Android Studio 模拟器或真机安装启动。
- 可以输入关键词并拿到在线搜索结果。
- 搜索结果在手机屏幕上可读、可滚动、可区分平台。
- 基础页面没有明显布局错位或触摸困难。

### 阶段 2：播放与移动端核心体验

目标是让 Android 端从搜索验证扩展为日常轻量播放器。

- 优化移动端导航和播放器布局。
- 接入歌曲播放、基础歌词和播放队列。
- 接入系统媒体通知与后台播放。
- 梳理登录态、Cookie 和缓存。
- 增加 Android 权限处理。
- 针对 WebView 兼容性补测试。

成功标准：

- 锁屏或后台状态下播放体验稳定。
- 搜索、播放、收藏、歌单等主流程可连续使用。
- 常见网络和鉴权错误有明确反馈。

### 阶段 3：高级能力评估

目标是决定是否继续追桌面端高级能力。

- 评估本地音乐库是否使用 Android MediaStore 重写。
- 评估外部插件体系是否迁移为受限沙箱或完全禁用。
- 评估离线缓存、下载和文件管理策略。
- 评估发布渠道和签名流程。

成功标准：

- 明确哪些能力进入 Android 正式版，哪些保持桌面端专属。

## 建议的首批代码入口

- `src/platform/`：新增 Android / Capacitor 平台服务。
- `src/services/platformService.ts`：确认平台服务调用是否需要扩展。
- `src/features/home/`：检查移动端首页与播放器入口。
- `src/components/SearchInput.vue` 与搜索相关组件：确认移动端搜索交互。
- `src/store/searchStore.ts`：确认在线搜索状态、错误和结果展示。
- `src/api/` 与 `src/utils/http/`：确认 Android WebView 下的接口访问策略。
- `docs/build.md`：后续补充 Android 构建命令和产物位置。

## 不建议一开始做的事

- 不建议直接把 Electron 主进程能力搬到 Android。
- 不建议先做完整本地音乐库扫描。
- 不建议首版就做播放、后台播放、登录和缓存。
- 不建议在没有移动端 UI 验证前承诺桌面端功能完全一致。
- 不建议把 Android 适配散落到页面组件里，应继续走平台服务收口。

## 初步工作量判断

| 范围             | 难度     | 说明                                           |
| ---------------- | -------- | ---------------------------------------------- |
| APK 启动验证     | 中低     | 主要是 Capacitor 工程、构建目录和运行时识别    |
| V1 UI 与在线搜索 | 中低到中 | 需要处理 WebView、接口访问、搜索状态和移动布局 |
| 在线播放 MVP     | 中       | 需要补播放链路、歌词、队列和基础媒体状态       |
| 后台播放与通知栏 | 中高     | 需要原生插件和 Android 生命周期处理            |
| 本地音乐库       | 高       | 需要重写文件权限、媒体库扫描和数据存储         |
| 插件体系迁移     | 高       | 现有外部插件运行时依赖桌面 Node 环境           |
| 桌面端完整平替   | 高       | 需要长期维护 Android 专属能力                  |

## 推荐决策

短期目标应定为 Android V1：移动端 UI 和在线搜索优先。等 APK 可运行、搜索链路稳定、移动端 UI 可用后，再决定是否投入播放、后台播放、本地音乐库和插件能力。
